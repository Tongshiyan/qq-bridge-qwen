## 4. 迁移中踩到的坑（都已解决）

1. **`mkdir "/home/ac/envs/qwen38" failed: No such file or directory`（rsync rc=11）**
   原因：目标机 `/home/ac/envs` 父目录不存在，而 rsync 只创建最后一级目录。
   解决：先 `mkdir -p /home/ac/envs`，然后重跑该目录的 rsync。

2. **公钥写入后老机仍然认证失败**
   原因：用 PowerShell 把公钥字符串经 ssh 参数传给远端时被转义；更隐蔽的是远端 `tr -d "\r"` 里的 `\r` 被 PowerShell 吃掉，变成 `tr -d r`，把公钥注释里的所有字母 `r` 都删了，key 行因此不合法（`ssh-keygen` 报 "not a public key file"）。
   解决：改为**文件级搬运**（scp 传 `.pub` 文件 → 远端脚本读取并校验 `ssh-keygen -lf` 后再追加），并在脚本里清掉 CR 污染与非法行。

3. **PowerShell → ssh 传参反复踩坑**
   `<`、`|`、`://`、`$i:`、含括号的命令行都会被 PowerShell 解析或吞引号；`$host` 是只读自动变量。
   解决：所有远端操作用「本地写脚本文件 → scp → `bash /tmp/x.sh`」，不再拼接远端命令行。

4. **迁移源本身就是「长上下文模式」**
   `bin/serve.sh` 与 `serve.long.sh` 完全一致（无 `--speculative-config`），所以迁过来后 2K 上下文解码实测 58 tok/s，而不是短模式应有的 ~95 tok/s。这是**忠实迁移**，想提速执行 `q38mode short`。

5. **Windows 侧遗留了一个旧隧道 keeper**
   有个 keeper 是用 `-EncodedCommand` 启动的，命令行里不含 `tunnel.ps1` 字样，按文本匹配抓不到，导致它反复重连老机 IP。已按「ssh 子进程的父进程」清理，并修正了切换脚本的识别逻辑。

6. **`pgrep -f 'vllm serve'` 自匹配**
   通过 ssh 内联执行时，远端 shell 的命令行本身包含该字符串，pgrep 会匹配到自己，误报“服务在跑”。脚本文件方式执行不会。

### 5.1 老机侧：没有 sudo 也要挡住开机自启

用户要求「不要开机自启、两台机器都手动启停」，但老机的 `qwen38.service` 是 `enabled`，而 `ac` 在该机**没有免密 sudo**（`sudoers.d/qwen38` 只放行 `systemctl start|stop|restart`，不含 `disable`）。

于是改用「不碰 root 的中和」：

| 文件 | 改动 | 依据 |
|---|---|---|
| `bin/serve.sh` | shebang 之后插入 guard：`[ -n "$INVOCATION_ID" ]` **或** `/proc/self/cgroup` 含 `qwen38.service` 时打印提示并 `exit 0` | systemd 启动的服务必然带 cgroup 归属与 `INVOCATION_ID`；而 setsid 直启两者都没有 |
| `bin/q38` | 换成与二卡机一致的 setsid 版（0 处 systemctl），于是手动启停不再经过 systemd | 与二卡机统一，也让控制台一套逻辑管两台 |
| `bin/q38mode` | status 行由 `systemctl is-active` 改为 `pgrep` | 同上 |
| 备份 | `*.orig-systemd` 三个文件 | 可一键还原 |

**实测证据（老机现场）**

| 检查 | 结果 |
|---|---|
| 模拟 systemd 拉起：`INVOCATION_ID=dummy bash serve.sh` | 打印「开机自启已停用…拒绝启动」，**退出码 0**，`pgrep -f "vllm serve"` 为空 —— 没加载模型、没占 GPU |
| `q38` 静态检查 | `pkill -f` 1 处、`systemctl` 0 处、`bash -n` OK |
| `serve.sh` 静态检查 | guard 在位、`--tensor-parallel-size 2` 等启动参数完好、`bash -n` OK |
| 手动启停链路（用伪造的 `vllm serve` 进程验证，避免占卡） | `q38 status` → 「服务：运行中」；`q38 stop` → 进程被杀 + 生成 STOPPED 标记 |
| 当前状态 | 8000 无监听、无 vllm 进程；`qwen38.service` 仍 enabled，但开机拉起会被上面这道 guard 拒绝 |

> 之所以用「伪造进程」而不是真启动：老机 GPU1 当时被同机用户 xiaohan 占着 5.8 GiB，
> TP=2 需要每卡约 21 GiB，直接启动必然 OOM，无法作为有效验证。

> 想彻底 `systemctl disable` 仍需 sudo 密码，见第 9 节遗留事项。

### 7.1 顺手修掉的控制台 bug（否则「手动启停」不成立）

| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | 点【停止】后隧道 5 秒又被拉起 | `Get-Keeper()` 只认 `-File ...tunnel.ps1` 启动的守护，而 `Start-TunnelAction` 自己是用 `-EncodedCommand` 启动的（命令行里没有 `tunnel.ps1` 字样） | 增加「谁是我们隧道 ssh 进程的父进程」判定；实测旧逻辑 0 命中 / 新逻辑 1 命中 |
| 2 | 二卡机服务明明在跑，控制台却显示「未运行」 | `Refresh-Server` 靠匹配 systemd 的 `active (running)` 判断状态，而二卡机是无 systemd 版 `q38`，输出是 `服务：运行中` | 正则改为 `服务：运行中\|active \(running\)`，两台机器都能识别 |

> 打补丁时又踩了一次本机编码坑：会话 shell 是 **Windows PowerShell 5.1 + ANSI 代码页 936**，
> 无 BOM 的 UTF-8 `.ps1` 会被按 GBK 解析，脚本里的中文字符串全部乱码、替换匹配数为 0。
> 给补丁脚本加上 UTF-8 BOM 后一切正常。

DSH 里的自定义 provider 无需改动（隧道仍映射本地 8000）。

```bash
# Windows 隧道切回老机
powershell -ExecutionPolicy Bypass -File C:\Users\<your-username>\Desktop\qwen\migrate\cutover-windows.ps1 -Server ac@your-old-server-ip
```

老机 `qwen38.service` 仍为 enabled（开机尝试启动）。彻底停用（需 sudo 密码）：
```bash

```
